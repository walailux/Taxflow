# infra — โครงสร้าง ver18, วิธีรัน และสถานะการย้ายระบบ

เอกสารนี้เป็นคู่มือปฏิบัติสำหรับการย้ายระบบ TaxFlow จาก ver17.2 ไป ver18
คู่มือ deploy ฉบับเต็มและคู่มือกู้คืนระบบเป็นงานของ **WP7** จะมาเติมในไฟล์นี้ภายหลัง

## 2. วิธีรัน

```bash
npm install                 # ติดตั้งครั้งเดียวที่โฟลเดอร์บนสุด (npm workspaces)
cp infra/.env.example apps/api/.env
npm start                   # เท่ากับ node apps/api/server.js
npm test                    # ชุดทดสอบ 192 ข้อ
```

เปิด <http://localhost:4000> จะได้หน้าเว็บเดิมของ ver17.2 เหมือนก่อนทุกประการ

**หน้าเว็บ React (WP2)** เปิด Windows PowerShell สองหน้าต่างที่โฟลเดอร์บนสุด

```powershell
npm start            # หน้าต่างที่ 1: API ที่พอร์ต 4000
npm run dev:web      # หน้าต่างที่ 2: หน้าเว็บ React ที่ http://localhost:5173
npm run test:web     # ชุดทดสอบฝั่งหน้าเว็บ (Vitest)
```

Vite ส่งต่อคำขอ `/api` ไปที่พอร์ต 4000 ให้เอง (proxy) จึงไม่ต้องตั้ง `COOKIE_CROSS_SITE` หรือ `AUTH_HEADER_MODE` ตอนพัฒนา
หน้าที่ยังไม่ได้ย้าย ระบบส่งต่อไปหน้าเว็บเดิมที่พอร์ต 4000 โดยใช้ session เดียวกัน (คุกกี้ไม่แยกตามพอร์ต)

บัญชีทดลอง (รหัสผ่าน `123456` ทุกบัญชี) — ระบบสร้างให้อัตโนมัติเมื่อฐานข้อมูลยังว่าง

| บัญชี | บทบาท |
|---|---|
| `creator@taxflow.test` | ครีเอเตอร์ |
| `agency@taxflow.test` | เอเจนซี่ |
| `brand@taxflow.test` | บริษัท |
| `admin@taxflow.test` | ผู้ดูแลระบบ |

## 3. การแยกหน้าเว็บออกจาก API

API (พอร์ต 4000) เป็น API ล้วน ตอบเฉพาะ JSON และไฟล์ (PDF/XML/ZIP) ไม่เสิร์ฟหน้าเว็บใดๆ
หน้าเว็บทุกหน้า รวมถึงภาพรวมระบบ คู่มือ นโยบายความเป็นส่วนตัว กฎหมาย และหน้าตรวจสอบเอกสาร (`/verify-doc`)
เป็น React ที่ `apps/web` (พอร์ต 5173) เปิด <http://localhost:4000> ตรงๆ จะเห็นหน้าสถานะ React ที่ build แยกไว้ใน `apps/web/dist-status`
(`npm run dev:all` build ใหม่ให้อัตโนมัติทุกครั้งที่บันทึกไฟล์ ต้องกดรีเฟรชเอง · ตอนไม่ได้รัน dev:all ใช้ `npm run build:status`)
หน้าอื่นที่เปิดผิดพอร์ต เช่น localhost:4000/login ถูกส่งต่อไปหน้าเดียวกันที่พอร์ต 5173
QR บนเอกสารชี้ไปที่ `PUBLIC_BASE_URL/verify-doc?token=...` (ลิงก์ `/verify.html` เดิมยังเปิดได้ หน้าเว็บส่งต่อให้เอง)

**CORS และ CSRF** ตั้งโดเมนหน้าเว็บที่อนุญาตใน `WEB_ORIGINS` (คั่นด้วยจุลภาค)
ระบบไม่ใช้ `*` เพราะคำขอต้องแนบคุกกี้ session และเบราว์เซอร์ห้ามใช้ `*` คู่กับ credentials
คำขอที่เปลี่ยนข้อมูล (POST/PUT/PATCH/DELETE) ซึ่งมี `Origin` นอกรายชื่อจะถูกปฏิเสธด้วย 403

**ถ้าเบราว์เซอร์บล็อกคุกกี้ข้ามโดเมนตอนทดสอบ** (ความเสี่ยงที่แผน WP1 ระบุไว้)
ให้ตั้ง `AUTH_HEADER_MODE=1` แล้วฝั่งหน้าเว็บส่ง token ทาง `Authorization: Bearer` แทนคุกกี้

> **แก้ไขระหว่าง WP2** ตัวแปร `COOKIE_CROSS_SITE` และ `AUTH_HEADER_MODE` ถูกเขียนไว้ในเอกสารและ `core/cors.js`
> ตั้งแต่ WP1 แต่ `lib/auth.js` ยังไม่ได้อ่านค่า (คุกกี้เป็น `SameSite=Lax` ตายตัว และไม่รับ Bearer)
> ตอนนี้ทำงานจริงแล้ว: `COOKIE_CROSS_SITE=1` ได้คุกกี้ `SameSite=None; Secure`
> ส่วน `AUTH_HEADER_MODE=1` API ส่ง token กลับทาง header `X-Session-Token` และรับ `Authorization: Bearer`
> ซึ่ง `apps/web/src/lib/api.js` จัดการให้อัตโนมัติ ค่าเริ่มต้นทำงานเหมือนเดิมทุกประการ (ทดสอบใน `test/authmode.test.js`)

## 5. ทดสอบ API ครบทุกเส้นทาง

```bash
npm test          # ชุดทดสอบหน่วย 192 ข้อ (ตรรกะภาษี เอกสาร PDF ลายมือชื่อ และรายชื่อเส้นทาง)
npm run test:api  # ยิงคำขอ HTTP จริงเข้า API ครบ 113 เส้น ใช้เวลาราว 50 วินาที
```

`test:api` เปิดเซิร์ฟเวอร์เองบนฐานข้อมูล SQLite และที่เก็บไฟล์ในโฟลเดอร์ชั่วคราว แล้วลบทิ้งเมื่อจบ
**ไม่แตะ Supabase จริง** แม้ `.env` จะตั้งค่าไว้ (สคริปต์ล้าง `DATABASE_URL` และ `S3_*` ก่อนเปิดเซิร์ฟเวอร์เสมอ)
ยิงตามลำดับการใช้งานจริง: สมัคร → เข้าสู่ระบบด้วย OTP ครบ 4 บทบาท → สร้างเอกสาร → ออก PDF/XML →
ลงนามด้วย OTP → ส่งคู่ค้าทั้งขอตรวจสอบ ขอลายเซ็น ตีกลับ ยกเลิก → ปฏิทิน คลังเอกสาร KYC ผู้ดูแลระบบ →
API key และ webhook → TOTP → ออกจากระบบ → ลบบัญชีตาม PDPA

นอกจากกรณีสำเร็จ ยังตรวจกรณีที่ต้องถูกปฏิเสธด้วย เช่น บัญชีอื่นเปิดเอกสารไม่ได้ (404)
ผู้ที่ไม่ใช่ผู้ดูแลระบบเข้าหน้าผู้ดูแลไม่ได้ (403) คำขอจากโดเมนอื่นถูกกัน CSRF (403)
ขอรหัส OTP ใหม่ทันทีต้องติดช่วงรอ 45 วินาที และรหัสเดิมใช้ไม่ได้หลังขอใหม่
ลายมือชื่อดิจิทัลถูกตรวจแบบครบวงจร ถ้าเครื่องมี `openssl` (แก้ไฟล์ 1 ไบต์แล้วต้องตรวจไม่ผ่าน)

สคริปต์ **ไม่ผ่าน** ถ้ามีเส้นทางใดใน `test/routes.expected.json` ไม่ถูกยิง ถ้ารหัสสถานะไม่ตรงที่คาด
หรือถ้าเซิร์ฟเวอร์ตอบ 5xx ไม่ว่ากรณีใด ใส่ `-- --verbose` เพื่อดูผลทีละคำขอ

**ผลล่าสุด:** 113 เส้น · 183 คำขอ · ผ่านทั้งหมด · ไม่มี 5xx

### บั๊กที่พบจากการยิงจริง

`POST /api/integrations/webhook/test` (ปุ่ม "ทดสอบ webhook") ตอบ 500 `ReferenceError: http is not defined`
ตั้งแต่ WP1 เพราะตอนแยก `server.js` ไฟล์ `routes/integrations.js` ไม่ได้นำ `require('http')` และ `require('https')`
ติดมาด้วย ชุดทดสอบเดิมตรวจแค่ว่าเส้นทางลงทะเบียนครบจึงจับไม่ได้ แก้แล้ว

หลังพบจุดนี้ได้สแกนทุกไฟล์ใน `apps/api` และ `packages/shared` ด้วยตัวแยกไวยากรณ์ (acorn)
หาชื่อตัวแปรที่ถูกใช้แต่ไม่เคยประกาศ ไม่พบจุดอื่นอีก

ด่านกัน CSRF (`core/cors.js`) เดิมปฏิเสธคำขอเปลี่ยนข้อมูลทุกคำขอที่ Origin ไม่อยู่ใน `WEB_ORIGINS`
รวมถึงคำขอจากหน้าเว็บที่ API เสิร์ฟเองบนโดเมนเดียวกัน ถ้าเปิดหน้าเว็บเดิมจากโดเมนที่ไม่ได้ใส่ในรายชื่อ
(พอร์ตอื่นในเครื่อง หรือโดเมนของผู้ให้บริการตอน WP7) ทุกปุ่มที่ส่งข้อมูลจะขึ้นว่า "คำขอมาจากโดเมนที่ไม่ได้รับอนุญาต"
แก้ให้คำขอจากโดเมนเดียวกันผ่านเสมอ คำขอจากโดเมนอื่นยังถูกปฏิเสธเหมือนเดิม (มีกรณีทดสอบทั้งสองแบบ)

### ยังต้องตรวจด้วยตาในเบราว์เซอร์

`test:api` ตรวจ API ไม่ได้ตรวจหน้าเว็บ รายการนี้ยังต้องลองเองบนหน้าเว็บเดิม
(หรือรอการทดสอบ Playwright ใน WP8)

1. หน้าจอทุกหน้าแสดงผลและกดปุ่มได้ ทั้ง 4 บทบาท
2. ตัวช่วยสร้างเอกสารครบ 14 ประเภท รวมใบกำกับภาษีอิเล็กทรอนิกส์ที่เพิ่งเปิดให้ใช้บนหน้าเว็บ
3. วาดลายเซ็นบน canvas และอัปโหลดไฟล์แบบลากวาง
4. สแกน QR บนไฟล์ PDF ด้วยมือถือแล้วเปิดหน้าตรวจสอบได้
5. เปิด PDF ที่ลงนามแล้วใน Adobe Acrobat Reader

## 6. ตั้งค่า Supabase (WP3 + WP4)

### 6.1 สร้างโปรเจกต์และฐานข้อมูล

1. สร้างโปรเจกต์ใหม่ที่ supabase.com เลือกภูมิภาคที่ใกล้ไทยที่สุด (Singapore) เพื่อลดเวลาตอบสนอง
2. กดปุ่ม **Connect** ด้านบน แล้วเลือก **Session pooler** (ไม่ใช่ Direct connection)

   Direct connection (`db.<ref>.supabase.co`) ใช้ IPv6 อย่างเดียว เน็ตที่เป็น IPv4 ล้วน
   ซึ่งเป็นส่วนใหญ่ในไทย จะขึ้น `ENOTFOUND` ทันที Session pooler รองรับ IPv4
   และเป็นตัวที่ผู้ให้บริการโฮสต์ API ส่วนใหญ่ต้องใช้อยู่แล้วตอนขึ้นคลาวด์จริง

   สังเกตว่าชื่อผู้ใช้เปลี่ยนจาก `postgres` เป็น `postgres.<project-ref>` ด้วย ไม่ใช่แค่ชื่อโฮสต์
3. ใส่ลงใน `apps/api/.env` เป็น `DATABASE_URL=...`
4. ตรวจว่าไฟล์ตั้งค่าถูกต้องก่อน

```bash
npm run env:check     # บอกว่าระบบอ่านค่าอะไรได้บ้าง โดยปิดบังรหัสผ่านไว้
npm run db:check      # ลองเชื่อมต่อจริงแล้วบอกว่าติดตรงไหน
```

จุดที่พลาดบ่อยที่สุดคือลืมลบเครื่องหมาย `#` หน้าบรรทัด สคริปต์นี้จะบอกให้ว่าบรรทัดไหนยังปิดอยู่

5. สร้างตารางทั้ง 17 ตาราง

```bash
npm run db:setup      # รัน sql/postgres-schema.sql ให้เอง ไม่ต้องติดตั้ง psql
```

6. ย้ายข้อมูลเดิมจาก SQLite ขึ้นไป (ข้ามได้ถ้ายอมให้ระบบสร้างบัญชีทดลองใหม่)

```bash
npm run db:migrate            # รายงานอย่างเดียว ยังไม่เขียนอะไร
npm run db:migrate -- --apply # ย้ายจริง
```

สคริปต์ย้ายข้อมูลรักษา `id` เดิมทุกแถว เพราะข้อมูลอ้างอิงกันด้วย id
(`documents.userId`, `attachments.docId`, `requests.docId`) ถ้าปล่อยให้ออก id ใหม่
ความสัมพันธ์ทั้งหมดจะพัง และย้ายตัวนับเลขที่เอกสารไปด้วย เลขที่เอกสารใหม่จึงเดินต่อจากของเดิม
ไม่ย้อนกลับไปชนเลขที่เคยออกไปแล้ว ทุกอย่างอยู่ใน transaction เดียว ถ้าพลาดกลางทางจะไม่เหลือข้อมูลค้าง

### 6.2 ที่เก็บไฟล์

1. Storage > Buckets สร้างสองถัง ตั้งเป็น Private ทั้งคู่

   * `taxflow-private` ไฟล์ทุกชนิดของระบบตอนนี้
   * `taxflow-public` เตรียมไว้สำหรับไฟล์ PDF/XML ที่ต้องเปิดผ่านลิงก์ตรวจสอบเอกสารใน WP5

2. Storage > S3 Configuration เปิด S3 protocol แล้วสร้าง access key
3. ใส่ค่าลงใน `apps/api/.env`

```
S3_ENDPOINT=https://<project_ref>.storage.supabase.co/storage/v1/s3
S3_REGION=<region ที่แสดงในหน้า S3 Configuration>
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_BUCKET_PRIVATE=taxflow-private
S3_BUCKET_PUBLIC=taxflow-public
```

4. ติดตั้งไลบรารีสำหรับคุยกับ S3 (เป็น optional dependency ไม่ต้องติดตั้งถ้ายังรันในเครื่อง)

```bash
npm install @aws-sdk/client-s3 @aws-sdk/s3-request-presigner -w @taxflow/api
```

5. ย้ายไฟล์เดิมขึ้นคลาวด์

```bash
npm run files:migrate             # รายงานอย่างเดียว
npm run files:migrate -- --apply  # ย้ายจริง
```

**ห้ามลบ `data/uploads` จนกว่าจะตรวจแล้วว่าเปิดไฟล์ได้ครบทุกประเภทจากระบบบนคลาวด์**

### 6.3 กลไกของชั้นจัดเก็บไฟล์

`lib/storage.js` เป็นจุดเดียวที่ระบบอ่านเขียนไฟล์ และเลือกปลายทางเองตามตัวแปรแวดล้อม
ไม่ตั้ง `S3_ENDPOINT` ก็เขียนลงดิสก์เหมือนเดิม ตั้งครบเมื่อไรก็ย้ายไป Supabase ทันที
โดยโค้ดส่วนอื่นไม่ต้องรู้ว่าปลายทางคืออะไร

ไฟล์ทุกไฟล์ถูก **เข้ารหัส AES-256-GCM ก่อนอัปโหลด** และถอดรหัสหลังดาวน์โหลด
กุญแจอยู่ที่ฝั่งเรา (`FILE_ENCRYPTION_KEY` หรือ `data/file.key`) ไม่ได้อยู่กับผู้ให้บริการ
ดาวน์โหลดไฟล์จากหน้า Supabase ตรง ๆ จะได้ไบต์ที่เปิดไม่ออก ซึ่งเป็นเกณฑ์ตรวจรับของ WP4

จุดที่เปลี่ยนพฤติกรรมจาก ver17.2 คือ **ไฟล์แนบเอกสาร โลโก้ และตราประทับ เดิมเก็บแบบไม่เข้ารหัส
ตอนนี้เข้ารหัสด้วย** ทำให้ชื่อไฟล์เปลี่ยน (เติม `.enc`) สคริปต์ย้ายไฟล์จึงตามไปแก้ชื่อในฐานข้อมูลให้
และ `storage.get()` ยังอ่านไฟล์ชื่อแบบเดิมที่ไม่เข้ารหัสได้อยู่ ข้อมูลเดิมจึงไม่พังแม้ยังไม่ได้ย้าย

### 6.4 สำรองข้อมูล

แผนฟรีของ Supabase ไม่มีไฟล์สำรองอัตโนมัติให้ดาวน์โหลด ควรรันคำสั่งนี้เป็นระยะ
โดยเฉพาะก่อนวันนำเสนอ

```bash
npm run db:backup      # ได้ไฟล์ JSON ใน apps/api/backups/
```

ไฟล์สำรองมีข้อมูลส่วนบุคคลของผู้ใช้อยู่ด้วย ให้เก็บไว้นอกที่เก็บโค้ด

### 6.5 ข้อควรระวังของแผนฟรี

* โปรเจกต์ที่ไม่มีการใช้งานราวหนึ่งสัปดาห์จะถูกพักอัตโนมัติ ต้องเข้าไปปลุกและซ้อมเปิดระบบ
  ล่วงหน้าอย่างน้อยหนึ่งวันก่อนนำเสนอ
* จำนวนการเชื่อมต่อฐานข้อมูลพร้อมกันมีจำกัด ระบบจึงตั้งเพดาน connection pool ไว้ที่ 10
  และปิดการเชื่อมต่อที่ว่างเกิน 30 วินาที ปรับได้ด้วย `PGPOOL_MAX`
* พื้นที่ไฟล์รวม 1 GB และจำกัดไฟล์ละ 50 MB ระบบยังคงเพดาน 5 MB ต่อไฟล์ตามเดิมอยู่แล้ว

## 7. ข้อควรรู้เมื่อรันบน Windows

* `lib/store.js` มีเมธอด `close()` สำหรับปิดไฟล์ฐานข้อมูล ชุดทดสอบเรียกก่อนลบโฟลเดอร์ชั่วคราวเสมอ
  เพราะ Windows ไม่ยอมให้ลบไฟล์ที่ยังมีโปรเซสเปิดค้างอยู่ (ขึ้น `EPERM`)
  ส่วนลินุกซ์และ macOS ลบไฟล์ที่ยังเปิดอยู่ได้ จึงไม่เคยเห็นปัญหานี้บนสองระบบนั้น
* คำสั่งที่ต้องส่งอาร์กิวเมนต์ต่อท้ายต้องคั่นด้วย `--` เสมอ เช่น `npm run db:migrate -- --apply`
  สคริปต์ที่ root ปิดท้ายด้วย `--` ไว้แล้ว อาร์กิวเมนต์จึงส่งผ่านชั้น workspace ไปถึงสคริปต์จริง
* สคริปต์ที่เขียนข้อมูล (`db:migrate`, `files:migrate`) **ไม่เขียนอะไรเลยถ้าไม่ใส่ `--apply`**
  ออกแบบไว้แบบนี้เพราะการย้ายข้อมูลย้อนกลับไม่ได้ ถ้าค่าเริ่มต้นคือย้ายเลย
  การพิมพ์คำสั่งผิดครั้งเดียวก็เขียนทับข้อมูลได้ทันที

## 8. เอกสาร e-Tax และ PDF/A-3 (WP5)

### 8.1 สิ่งที่เพิ่มเข้ามา

| `lib/xmlbuild.js` | สร้างไฟล์ XML ตามโครงสร้าง ขมธอ. 3-2560 ของ ETDA | ใช่ |
| `lib/docplan.js` | แปลงเอกสารเป็นแผนผังการวาด (ตรรกะบริสุทธิ์) | ใช่ |
| `lib/pdfbuild.js` | วาดด้วย PDFKit แล้วแปลงเป็น PDF/A-3 พร้อมแนบ XML | ส่วนที่ไม่ต้องใช้ PDFKit |
| `lib/thaiwrap.js` | ตัดบรรทัดภาษาไทยตรงรอยต่อของคำ | ใช่ |

### 8.2 ติดตั้งก่อนใช้งาน

```bash
npm install pdfkit @cantoo/pdf-lib -w @taxflow/api
```

แล้ววางไฟล์ฟอนต์ไทยตามขั้นตอนใน `apps/api/assets/fonts/README.md`
PDF/A ห้ามใช้ฟอนต์ที่ไม่ฝังลงในไฟล์ จึงข้ามขั้นตอนนี้ไม่ได้

### 8.3 ตรวจเอกสารต้นแบบ

แผน ver18 เฟส 2 ระบุให้ทำเอกสารต้นแบบหนึ่งประเภทให้ผ่านก่อน แล้วจึงขยายไปประเภทที่เหลือ

```bash
npm run pdf:sample                       # ได้ apps/api/out/sample-ETAX_INVOICE.pdf
verapdf --flavour 3b apps/api/out/sample-ETAX_INVOICE.pdf
```

veraPDF ดาวน์โหลดจาก verapdf.org ใช้ตอนพัฒนาเท่านั้น ไม่ต้องติดตั้งบนเครื่องที่ deploy

**สิ่งที่ต้องดูด้วยตาเพิ่มจากผลของ veraPDF**

1. สระและวรรณยุกต์ไทยลอยถูกตำแหน่ง ดูคำว่า "ผู้ซื้อ" และ "เกื้อกูล" ในไฟล์ตัวอย่าง
2. ตัวเลขเงินมีลูกน้ำคั่นหลักพันครบและทศนิยม 2 ตำแหน่ง
3. เปิดแถบไฟล์แนบในโปรแกรมอ่าน PDF แล้วเห็นไฟล์ XML อยู่ข้างใน
4. มีข้อความกำกับว่าเป็นการสาธิต

ถ้า veraPDF ไม่ผ่าน ให้ส่งรายการ error ทั้งก้อนมา อย่าเพิ่งไปทำเอกสารประเภทที่เหลือ

### 8.4 สิ่งที่ต่างจากแผนเดิม

| แผนระบุ | ที่ทำจริง | เหตุผล |
|---|---|---|
| `xmlbuilder2` สร้าง XML | เขียนเอง ไม่พึ่งไลบรารีภายนอก | โครงสร้างเป็นต้นไม้คงที่ เขียนเองแล้วทดสอบได้ครบ 21 ข้อ |
| PDFKit ทำ PDF/A-3 | PDFKit วาด + `@cantoo/pdf-lib` แปลงเป็น PDF/A-3 | PDFKit ไม่มี XMP, OutputIntent, ICC profile และ `/AF` ให้ ต้องไปแก้โครงสร้างภายในซึ่งพังง่ายเมื่ออัปเกรดรุ่น |

ทั้งสองจุดควรระบุในรายงานให้ตรงกับของจริง

**เรื่องที่ต้องแก้ในรายงาน** ชื่อย่อมาตรฐานที่ถูกต้องคือ **ขมธอ. 3-2560** ไม่ใช่ มพศ. 3-2560

### 8.5 ต่อเข้ากับปุ่ม PDF และขยายครบทุกประเภท

**เอกสารทั้ง 14 ประเภทออกเป็น PDF/A-3 แล้ว** ไม่ใช่เฉพาะกลุ่ม e-Tax
ขั้นตอนแปลงเป็น PDF/A-3 (XMP, OutputIntent, คู่ /ID) ไม่ขึ้นกับว่ามีไฟล์แนบหรือไม่
จึงไม่ต้องใช้ทางเลือกลดความเสี่ยงข้อ 1 ของแผน (ลดเหลือเฉพาะเอกสารภาษี)
ไฟล์ XML มีเฉพาะใบกำกับภาษีและใบรับอิเล็กทรอนิกส์ ตามที่ ขมธอ. 3-2560 ครอบคลุม

| กลุ่ม | เอกสาร | รูปแบบบนกระดาษ |
|---|---|---|
| การเงิน | ใบเสนอราคา · PO · ใบแจ้งหนี้ · ใบเสร็จ · ใบส่งมอบงาน · ใบสำคัญจ่าย · ใบกำกับภาษี · ใบรับ | หัวกระดาษ คู่ค้า ตารางรายการ ยอดรวม |
| สัญญา | สัญญากับ Brand · สัญญาจ้าง Influencer | ชื่อเรื่องกลางหน้า ข้อสัญญาเรียงเลข ช่องลงนาม + พยาน 2 คน อากรแสตมป์ |
| มอบอำนาจ | หนังสือมอบอำนาจ | ช่องติดอากร 10/30 บาท ช่องติ๊กเรื่องที่มอบ |
| ภาษี | 50 ทวิ | ช่องเลขผู้เสียภาษี 13 ช่อง ตารางเงินได้ 7 บรรทัด ออก 2 ฉบับ |
| ภาษี | ภ.ง.ด.3 · ภ.ง.ด.53 | ใบหน้าแบบ + ใบแนบแผ่นละ 8 ราย แบ่งหน้าอัตโนมัติ |

| `GET /api/documents/:id/pdf?download=1` | บังคับดาวน์โหลดแทนการเปิดในแท็บ |
| `GET /api/documents/:id/pdf?format=html` | หน้าพิมพ์ HTML แบบเดิมของ ver17.2 |
| `GET /api/documents/:id/xml` | ไฟล์ XML ของเอกสาร e-Tax (ไฟล์เดียวกับที่แนบใน PDF) **เส้นทางใหม่ รวมเป็น 112 เส้น** |
| `GET /api/requests/:id/pdf` | ผู้รับเอกสารได้ PDF/A-3 ฉบับเดียวกับเจ้าของ |
| `GET /api/documents/export-zip` | ZIP ของไฟล์ PDF/A-3 (และ XML) เดิมเป็นไฟล์ HTML |

ปุ่ม "PDF" ในหน้าเว็บเดิมชี้มาที่ `/pdf` อยู่แล้ว จึงได้ไฟล์ใหม่ทันทีโดยไม่ต้องแก้ลิงก์
หน้ารายละเอียดเอกสารเพิ่มปุ่ม "ดาวน์โหลด PDF" "ดาวน์โหลด XML" และ "หน้าพิมพ์ (HTML)"

**ทางถอยเมื่อสร้าง PDF ไม่ได้** เช่น ยังไม่ได้ติดตั้งไลบรารี ยังไม่ได้วางฟอนต์ หรือข้อมูล e-Tax ไม่ครบตามมาตรฐาน
ระบบแสดงหน้า HTML เดิมพร้อมแถบสีแดงบอกสาเหตุ และเขียนบรรทัด `[pdf]` ลง log ของเซิร์ฟเวอร์
ผู้ใช้จึงเปิดเอกสารได้เสมอ ไม่เจอหน้า error ระหว่างสาธิต

### 8.6 การเก็บไฟล์และ cache (`lib/docfile.js`)

วาดไฟล์ครั้งแรกแล้วเก็บบน Storage ครั้งถัดไปอ่านไฟล์เดิม (ทดสอบจริง: วาด 781–902 ms · อ่านซ้ำ 6–7 ms)
ระบบวาดใหม่เองเมื่อสิ่งที่ **เห็นบนกระดาษ** เปลี่ยน ได้แก่ เนื้อหา เลขที่ สถานะ ลายเซ็นทั้งสองฝ่าย
โลโก้ ตราประทับ ลิงก์ตรวจสอบ (QR) และรุ่นของโค้ดวาด (`RENDER_VERSION`)
ไฟล์เก่าถูกลบหลังบันทึกไฟล์ใหม่สำเร็จแล้วเท่านั้น

> **แก้โค้ดวาดจนหน้าตาเปลี่ยน ให้เพิ่ม `RENDER_VERSION` ใน `lib/docfile.js`**
> มิฉะนั้นผู้ใช้จะได้ไฟล์รุ่นเก่าที่ cache ไว้

**ทำไมเก็บในถังส่วนตัว ไม่ใช่ถังสาธารณะตามที่แผนเขียนไว้**
เอกสารภาษีมีชื่อ ที่อยู่ เลขประจำตัวผู้เสียภาษี และยอดเงิน ซึ่งเป็นข้อมูลส่วนบุคคล
ถังสาธารณะไม่เข้ารหัสและเปิดตรงได้ ขัดทั้งเกณฑ์ WP4 ข้อ "ไฟล์บนคลาวด์เปิดตรงไม่ได้" และหลัก PDPA ของระบบ
ไฟล์ PDF/XML จึงเข้ารหัส AES-256-GCM เหมือนไฟล์อื่น และเปิดได้ทางเดียวคือผ่าน API ที่ตรวจสิทธิ์แล้ว
ถัง `taxflow-public` ยังไม่มีไฟล์ใช้งาน **ควรระบุการเปลี่ยนแปลงนี้ในรายงาน**

ข้อมูลไฟล์บันทึกที่ `doc.file` และถูกตัดออกจาก `contentHash` (`core/context.js`)
ถ้าไม่ตัด แค่กดดู PDF หลังลงนามก็ทำให้หน้าตรวจสอบรายงานว่าเอกสารถูกแก้ไข (มีชุดทดสอบกันไว้)
หน้าเว็บไม่เห็นชื่อไฟล์จริงบน Storage เห็นเพียงขนาด เวลาที่สร้าง และมี XML หรือไม่

ลบแบบร่างหรือลบบัญชีตาม PDPA ระบบลบไฟล์ PDF/XML ที่ cache ไว้ด้วย
ส่วนตัวเอกสารภาษียังเก็บครบตามมาตรา 87/3 และสร้าง PDF ใหม่ได้ทุกเมื่อ

### 8.7 ข้อบกพร่องที่พบตอนต่อเข้าระบบจริง

1. **เอกสารจริงออก XML ไม่ได้** เอกสารที่บันทึกจริงเก็บคู่ค้าไว้ที่ `partyInfo` ส่วน `party` เป็นแค่ชื่อ
   แต่ตัววาดและตัวสร้าง XML อ่าน `party` ตรง ๆ ใบกำกับภาษีจากระบบจริงจึงถูกปฏิเสธว่า "ไม่มีชื่อผู้ซื้อ"
   ทั้งที่ข้อมูลครบ ไฟล์ตัวอย่างไม่เจอปัญหานี้เพราะส่ง `party` เป็นก้อนมาเอง
   แก้ด้วย `lib/docshape.js` เป็นจุดเดียวที่แปลงรูปร่างเอกสาร
2. **หน้าเว็บออกเอกสาร e-Tax ไม่ได้** หน้าเว็บเดิมโหลดสำเนา `docschema.js` รุ่นก่อน WP5 ของตัวเอง
   ตอนนี้ API ส่งไฟล์จาก `packages/shared` ตรง ๆ และลบสำเนาทิ้งแล้ว
3. **หน้าพิมพ์ HTML ไม่มีแม่แบบของเอกสาร e-Tax** เพิ่มแล้ว ใช้เป็นทางถอยได้ครบทุกประเภท

### 8.9 ผลตรวจเอกสารต้นแบบรอบแรก (ก่อนต่อเข้าระบบ)

ตรวจไฟล์ `sample-ETAX_INVOICE.pdf` ที่สร้างบนเครื่องจริงด้วย poppler และ pypdf

**โครงสร้าง PDF/A-3 ครบทุกข้อ**

| ข้อกำหนด | ผล |
|---|---|
| PDF เวอร์ชัน 1.7 | ผ่าน |
| ฝังฟอนต์ครบทุกตัวแบบ subset พร้อม ToUnicode | ผ่าน (Sarabun Regular และ Bold) |
| XMP metadata ไม่บีบอัด ประกาศ `pdfaid:part=3` `pdfaid:conformance=B` | ผ่าน |
| OutputIntent `GTS_PDFA1` ฝัง ICC profile `sRGB IEC61966-2.1` | ผ่าน |
| คู่ `/ID` ใน trailer | ผ่าน |
| `/AF` ใน catalog ชี้ไปยังไฟล์แนบ | ผ่าน |
| ไฟล์แนบ `AFRelationship=/Data` `Subtype=text/xml` มี `/Params` ครบ | ผ่าน |
| XML ที่แนบผ่านตัวตรวจของระบบ ยอดรวมตรงกับหน้า PDF | ผ่าน |

ผลตรวจด้วย veraPDF ยังต้องรอ เป็นตัวตัดสินสุดท้ายตามเกณฑ์ของแผน

**ข้อบกพร่องที่พบและแก้แล้ว**

1. **ตัดบรรทัดกลางคำไทย** คำว่า "สร้างสรรค์" ถูกหั่นเป็น "สร้างสรร" กับ "ค์" คนละบรรทัด
   เพราะภาษาไทยไม่เว้นวรรค PDFKit จึงมองทั้งประโยคเป็นคำเดียว
   แก้โดยเพิ่ม `lib/thaiwrap.js` ใช้ `Intl.Segmenter` ตัดคำก่อนส่งให้ PDFKit
2. **ตัว l หายตอนคัดลอกข้อความ** ฟอนต์รวม f กับ l เป็น ligature ตาเห็นถูก
   แต่คัดลอกอีเมลแล้วได้ `taxfow.test` และลิงก์ตรวจสอบเอกสารใช้ไม่ได้ แก้โดยปิด `liga` กับ `clig`
3. **ผลบวกคอลัมน์ไม่ตรงบรรทัดรวม** ตารางแสดงยอดหลังหักส่วนลด แต่บรรทัดรวมแสดงยอดก่อนหัก
   (เป็นมาตั้งแต่ระบบเดิม) แก้ให้บรรทัดรวมเริ่มจากผลบวกคอลัมน์ ยอด VAT และยอดสุทธิไม่เปลี่ยน

ทั้งสามข้อมีชุดทดสอบกันไม่ให้กลับมา

**ข้อจำกัดที่รู้และยังไม่แก้**

คัดลอกคำที่มีสระอำจาก PDF จะได้ "ำา" เกินมาหนึ่งตัว เช่น "กำกับ" กลายเป็น "กำากับ"
เกิดจากฟอนต์แยกสระอำเป็นสองรูปเพื่อวางนิคหิตให้ถูกตำแหน่ง ส่วนที่มองเห็นบนหน้ากระดาษถูกต้อง
ข้อนี้ไม่กระทบ PDF/A-3 ระดับ B ที่ตรวจเฉพาะการแสดงผล (ระดับ U จึงจะตรวจการแปลงกลับเป็นข้อความ)
และข้อมูลที่เครื่องอ่านจริงอยู่ในไฟล์ XML ที่แนบ ซึ่งถูกต้องทุกตัวอักษร
ถ้าจะแก้ต้องปิดฟีเจอร์ `ccmp` ของฟอนต์ ซึ่งเสี่ยงทำให้วรรณยุกต์ลอยผิดตำแหน่ง จึงไม่ทำ

## 9. เชื่อมต่อฐานข้อมูลไม่ได้ ทำยังไง

รัน `npm run db:check` ก่อนเสมอ สคริปต์นี้แยกสาเหตุออกจากกันให้ โดยไม่แสดงรหัสผ่าน
จึงส่งผลลัพธ์ให้คนอื่นช่วยดูได้อย่างปลอดภัย

มันลองเชื่อมต่อสองแบบเทียบกัน คือส่ง connection string ทั้งบรรทัดให้ไลบรารีแกะเอง
กับแยกชื่อผู้ใช้และรหัสผ่านออกเป็นค่าแยกโดยไม่ผ่านการแกะ URL
ผลที่ต่างกันบอกสาเหตุได้ทันที

| อาการ | แปลว่า | แก้ยังไง |
|---|---|---|
| `ENOTFOUND db.<ref>.supabase.co` | Direct connection เป็น IPv6 อย่างเดียว | เปลี่ยนไปใช้ Session pooler |
| แบบ B ผ่าน แบบ A ไม่ผ่าน | รหัสผ่านมีอักขระที่ทำให้ URL เพี้ยน | ย้ายรหัสไปไว้ใน `PGPASSWORD` แยกบรรทัด แล้วตัด `:รหัสผ่าน` ออกจาก `DATABASE_URL` |
| ไม่ผ่านทั้งสองแบบ | รหัสผ่านผิดจริง หรือยังไม่ได้กด Reset password | ดูรายการตรวจด้านล่าง |
| `Tenant or user not found` | ชื่อผู้ใช้ไม่มี project ref ต่อท้าย | แก้เป็น `postgres.<project-ref>` |

**รายการตรวจเมื่อรหัสผ่านไม่ผ่าน**

1. ในหน้า Reset database password ต้องกดปุ่ม **Reset password** สีเขียว
   แค่กด Copy แล้วปิดหน้าต่างไป รหัสใหม่ยังไม่ถูกตั้งจริง
2. รหัสที่ใช้คือ **Database password** ไม่ใช่รหัสที่ล็อกอินเข้าเว็บ Supabase
3. เพิ่งรีเซ็ตรหัส รอสัก 1-2 นาทีให้ pooler รับรู้ แล้วลองใหม่
4. ตั้งรหัสเป็นตัวอักษรอังกฤษกับตัวเลขล้วน ยาวสัก 20 ตัว
   ยาวพอก็แข็งแรงพอ และตัดปัญหาเรื่องอักขระพิเศษไปเลย
5. โปรเจกต์ต้องอยู่สถานะ Active ไม่ใช่ Paused

## 10. ป้าย RLS disabled ในหน้า Supabase

หน้า Table Editor ของ Supabase ขึ้นป้ายแดง `RLS disabled` และ `UNRESTRICTED` ข้างทุกตาราง
**เป็นการตั้งใจออกแบบไว้แบบนี้** ไม่ใช่การลืมตั้งค่า

Row Level Security คุมสิทธิ์ระดับแถวที่ชั้นฐานข้อมูล จำเป็นเมื่อเบราว์เซอร์คุยกับฐานข้อมูลตรง
ผ่าน supabase-js หรือ Data API แต่สถาปัตยกรรมของ TaxFlow คือ

```
หน้าเว็บ  →  API ของเรา (Express)  →  PostgreSQL
```

หน้าเว็บไม่เคยแตะฐานข้อมูลตรง ทุกคำขอผ่าน API ที่ตรวจสิทธิ์อยู่แล้วว่าผู้ใช้เห็นได้เฉพาะเอกสารของตัวเอง
และปิด Data API ของ Supabase ไว้ตั้งแต่ตอนสร้างโปรเจกต์ จึงไม่มีช่องทางเข้าถึงข้อมูลที่ไม่ผ่าน API ของเรา

ถ้าเปิด RLS โดยไม่เขียน policy ไว้ ระบบจะอ่านข้อมูลได้ 0 แถวโดยไม่มีข้อความ error ฟ้อง
ซึ่งไล่หาสาเหตุยากมาก จึงไม่เปิดสิ่งที่ไม่ได้เพิ่มความปลอดภัยให้สถาปัตยกรรมนี้

**ควรระบุเรื่องนี้ในรายงาน** เผื่อผู้ตรวจเห็นป้ายแดงตอนสาธิตแล้วถาม
คำตอบคือการควบคุมสิทธิ์อยู่ที่ชั้น API ไม่ใช่ชั้นฐานข้อมูล

## 11. ลายมือชื่อดิจิทัล (WP6)

### 11.1 ตั้งค่าครั้งแรก

```bash
npm run sign:setup          # สร้างกุญแจ RSA 3072 + ใบรับรองอายุ 3 ปี ด้วย OpenSSL
```

สคริปต์แสดงรหัสผ่านของกุญแจ **ครั้งเดียว** ให้นำไปใส่ใน `apps/api/.env`

```
SIGN_KEY_PASSPHRASE=รหัสที่แสดงบนจอ
```

แล้วเริ่มเซิร์ฟเวอร์ใหม่ ไฟล์อยู่ใน `apps/api/data/sign/` (อยู่ใน `.gitignore` ห้ามขึ้นที่เก็บโค้ด)
Windows ใช้ openssl ที่มากับ Git for Windows ได้ ไม่ตั้งค่าก็ไม่เป็นไร ระบบยังออก PDF/A-3 ได้ แต่ไม่มีลายมือชื่อ

### 11.2 ระบบลงนามเมื่อไร

เมื่อผู้ออกเอกสารกด "ลงนาม" และยืนยันรหัส OTP ทางอีเมลสำเร็จ (ขั้นตอนเดิมตั้งแต่ ver13 ไม่เปลี่ยน)
ไฟล์ PDF ที่ออกหลังจากนั้นจะมีลายมือชื่อดิจิทัลฝังอยู่ เอกสารที่ยังไม่มีคนลงนามได้ PDF/A-3 ธรรมดา
ระบบไม่ใส่ลายมือชื่อให้เอกสารที่ยังไม่มีใครลงนาม

| รายการ | ค่า |
|---|---|
| รูปแบบ | PAdES baseline B-B · `SubFilter /ETSI.CAdES.detached` |
| อัลกอริทึม | SHA-256 + RSA 3072 |
| Signed attributes | contentType · messageDigest · signingCertificateV2 |
| เวลาที่ลงนาม | `/M` ใน signature dictionary = เวลาที่ประทับลายมือชื่อลงไฟล์ (นาฬิกาเซิร์ฟเวอร์ ไม่ใช่ TSA) ส่วนเวลาที่ผู้ใช้ยืนยัน OTP บันทึกไว้ในเหตุผล (Reason) |
| ครอบคลุม | ทุกไบต์ของไฟล์ รวมไฟล์ XML ที่แนบอยู่ภายใน |
| ข้อความในลายมือชื่อ | ชื่อผู้ลงนาม และเหตุผล "ยืนยันตัวตนด้วยรหัส OTP ... ไม่มีผลรับรองตามกฎหมาย" |

### 11.3 ตรวจเกณฑ์ตรวจรับของแผน

**เปิดใน Adobe Acrobat Reader แล้วเห็นลายมือชื่อ**
ลงนามเอกสารในระบบ กดดาวน์โหลด PDF แล้วเปิดใน Adobe Reader แถบด้านบนจะแสดงลายมือชื่อ
และเตือนว่า "ตัวตนของผู้ลงนามไม่ทราบ" เป็นพฤติกรรมปกติของใบรับรองที่ออกเอง ตามความเสี่ยงที่แผนระบุไว้

ถ้าต้องการให้ขึ้นเครื่องหมายถูกสีเขียวตอนสาธิต ให้นำเข้า `apps/api/data/sign/taxflow-sign.cer`
ที่ Edit > Preferences > Signatures > Identities & Trusted Certificates > Trusted Certificates > Import
แล้วติ๊ก "Use this certificate as a trusted root" **ควรอธิบายขั้นตอนนี้ตอนนำเสนอ** ว่าเป็นการสั่งให้เครื่องนี้
เชื่อถือใบรับรองของเราเอง ไม่ได้ทำให้ใบรับรองมีผลทางกฎหมาย

**แก้ไฟล์แม้ไบต์เดียวแล้วต้องฟ้อง** มีสามทางให้เลือกตอนสาธิต

```bash
npm run sign:verify -- เอกสาร.pdf          # ตรวจจากบรรทัดคำสั่ง
```

* หน้าตรวจสอบเอกสาร `/verify.html` มีช่อง "ตรวจลายมือชื่อดิจิทัลของไฟล์ PDF" อัปโหลดไฟล์แล้วเห็นผลทันที
  (`POST /api/verify/pdf` ไม่ต้องเข้าสู่ระบบ ไม่เก็บไฟล์ จำกัด 20 ครั้งต่อ 10 นาทีต่อ IP)
* หน้าตรวจสอบจาก QR Code ตรวจลายมือชื่อในไฟล์ PDF จริงของเอกสารนั้นให้ด้วย
* Adobe Reader จะขึ้นว่าเอกสารถูกแก้ไขหลังลงนาม

วิธีแก้ไฟล์หนึ่งไบต์สำหรับสาธิต: เปิดไฟล์ PDF ด้วยโปรแกรมแก้ไขแบบ hex (เช่น HxD บน Windows)
เปลี่ยนตัวเลขใดก็ได้หนึ่งตัวแล้วบันทึก ห้ามใช้โปรแกรมแก้ PDF เพราะจะบันทึกทั้งไฟล์ใหม่

**แก้หลังทดสอบบนเครื่องจริง:** รุ่นแรกใส่เวลายืนยัน OTP ลงใน `/M` เอกสารที่ลงนามก่อนสร้างใบรับรองใบปัจจุบัน
จึงถูก Adobe รายงานว่า *Signer's identity is invalid because it has expired or is not yet valid* เพราะอ้างว่าลงนาม
ด้วยใบรับรองก่อนที่ใบรับรองนั้นจะมีอยู่ ตอนนี้ `/M` เป็นเวลาที่ประทับจริง และตัวตรวจของระบบตรวจอายุใบรับรอง
ณ เวลาลงนามแบบเดียวกับ Adobe แล้ว

### 11.4 ผลตรวจด้วยเครื่องมือภายนอก

ชุดทดสอบ `test/pdfsign.test.js` ไม่ได้เชื่อตัวตรวจของระบบเองอย่างเดียว แต่ยืนยันด้วยเครื่องมือสองตัวที่ไม่ได้เขียนเอง

| เครื่องมือ | ไฟล์ต้นฉบับ | ไฟล์ที่แก้ 1 ไบต์ |
|---|---|---|
| `openssl cms -verify` | CMS Verification successful | ไม่ผ่าน |
| `pdfsig` (Poppler/NSS แบบเดียวกับโปรแกรมอ่าน PDF) | Signature is Valid · Total document signed | Digest Mismatch |
| ตัวตรวจของระบบ | ผ่านทุกข้อ | "เนื้อหาไฟล์ถูกเปลี่ยนแปลงหลังจากลงนาม" |

ทดสอบการแก้ไบต์ที่ต้นไฟล์ กลางเนื้อหา ภายในไฟล์ XML ที่แนบ และท้ายไฟล์ รวมถึงการต่อข้อมูลท้ายไฟล์หลังลงนาม
หลังลงนามแล้วไฟล์ยังเป็น PDF/A-3B มี XML แนบ และ `qpdf --check` ไม่พบข้อผิดพลาด
ยังต้องรัน veraPDF กับไฟล์ที่ลงนามแล้วบนเครื่องจริงอีกครั้ง

### 11.5 สิ่งที่ต่างจากแผน ต้องระบุในรายงาน

| แผนระบุ | ที่ทำจริง | เหตุผล |
|---|---|---|
| node-signpdf + node-forge | เขียนเองด้วย `crypto` ของ Node.js + `lib/der.js` | ติดตั้งไลบรารีเพิ่มไม่ได้ และ Node 22 มี RSA/SHA-256/X.509 ในตัวครบ ความถูกต้องยืนยันด้วย openssl และ pdfsig |
| กุญแจเก็บเป็นไฟล์ `.p12` | ระบบอ่านไฟล์ `.pem` (PKCS#8 เข้ารหัสด้วยรหัสผ่าน) ส่วน `.p12` สร้างไว้ให้ใช้กับเครื่องมืออื่น | Node อ่าน PKCS#12 ไม่ได้ในตัว ความปลอดภัยเท่ากัน |
| ประทับเวลาจากเซิร์ฟเวอร์ | เวลาใน `/M` ตามที่ PAdES กำหนด | ไม่ใช่ตราประทับเวลาจาก TSA ตาม RFC 3161 |
| XAdES บนไฟล์ XML | **ยังไม่ทำ** ใช้ทางเลือกลดความเสี่ยงข้อ 2 ของแผน | XML ที่แนบใน PDF ได้รับการคุ้มครองโดยลายมือชื่อ PAdES อยู่แล้ว (แก้แล้วตรวจไม่ผ่าน) ส่วนไฟล์ XML ที่ดาวน์โหลดแยกยังไม่มีลายมือชื่อของตัวเอง |

**ความหมายของลายมือชื่อในระบบนี้ (ต้องอธิบายในรายงาน)** ใบรับรองเป็นของ "ระบบ TaxFlow" ใบเดียว
ไม่ใช่ของผู้ใช้แต่ละคน ระบบลงนามให้เมื่อผู้ใช้ยืนยันตัวตนด้วย OTP แล้ว และบันทึกชื่อผู้ลงนามไว้ในลายมือชื่อ
รูปแบบนี้ใกล้กับตราประทับอิเล็กทรอนิกส์ของผู้ให้บริการ มากกว่าลายมือชื่อรายบุคคล
และใบรับรองออกเอง ไม่ได้มาจากผู้ให้บริการออกใบรับรองที่ได้รับอนุญาต จึงไม่มีผลรับรองตามกฎหมาย

### 11.6 ขึ้นคลาวด์ (เตรียมไว้สำหรับ WP7)

ผู้ให้บริการส่วนใหญ่ไม่มีดิสก์ถาวร ให้ตั้งตัวแปรแวดล้อมสามตัวนี้แทนไฟล์ใน `data/sign/`

```
SIGN_KEY_PEM_B64=   base64 ของ taxflow-sign.key.pem (กุญแจยังเข้ารหัสอยู่)

SIGN_KEY_PASSPHRASE=
```

เปลี่ยนใบรับรองเมื่อไร ไฟล์ PDF ที่ cache ไว้จะถูกลงนามใหม่ด้วยใบปัจจุบันเองในครั้งถัดไปที่มีคนเปิด

## 12. เข้าสู่ระบบและสมัครด้วย Google

### 12.1 การทำงาน

* **สมัคร** กด "สมัครด้วย Google" ที่หน้าสมัคร (หรือกดปุ่ม Google ที่หน้าเข้าสู่ระบบด้วยบัญชีที่ยังไม่เคยสมัคร)
  ระบบใช้อีเมลและชื่อจาก Google ไม่ต้องตั้งรหัสผ่าน แต่ยังต้องกรอกบทบาท ข้อมูลผู้เสียภาษี ที่อยู่ และความยินยอมให้ครบ
  แล้วยืนยันรหัส OTP ที่ส่งไปอีเมล Google นั้นจริง บัญชีจึงเปิดใช้งาน
* **เข้าสู่ระบบ** กดปุ่ม Google แล้วยืนยัน OTP ทางอีเมลทุกครั้ง (บัญชีที่เปิด TOTP ใช้รหัสจากแอปแทน) เหมือนเข้าสู่ระบบด้วยรหัสผ่าน
* **บัญชีเดิมที่สมัครด้วยรหัสผ่าน** ถ้าอีเมลตรงกับบัญชี Google ระบบผูกให้อัตโนมัติ หลังจากนั้นเข้าได้ทั้งสองแบบ
  บัญชี Google อีกบัญชีที่อีเมลเดียวกันผูกซ้ำไม่ได้
* **ลบบัญชี** บัญชีที่สมัครด้วย Google ไม่มีรหัสผ่าน จึงยืนยันด้วย OTP ทางอีเมลแทน ระบบลบรหัสบัญชี Google ออกด้วย จึงสมัครใหม่ได้

API ตรวจลายเซ็นของ ID token กับกุญแจสาธารณะของ Google เอง (`lib/google.js`) พร้อมตรวจผู้ออก Client ID วันหมดอายุ
และต้องเป็นอีเมลที่ Google ยืนยันแล้ว ไม่ต้องติดตั้งไลบรารีเพิ่ม และไม่ต้องใช้ client secret

### 12.2 สร้าง Client ID (ทำครั้งเดียว)

1. เข้า <https://console.cloud.google.com/> สร้างโปรเจกต์ (หรือใช้โปรเจกต์เดิม)
2. **APIs & Services > OAuth consent screen** เลือก External กรอกชื่อแอป TaxFlow และอีเมลติดต่อ
   ระหว่างทดสอบ (Testing) เพิ่มอีเมลที่จะใช้ทดสอบใน **Test users** ด้วย ไม่งั้น Google จะไม่ให้เข้า
3. **APIs & Services > Credentials > Create credentials > OAuth client ID** เลือก **Web application**
4. **Authorized JavaScript origins** ใส่ทั้งสองบรรทัด (Google ต้องการ `http://localhost` แยกด้วยเมื่อทดสอบในเครื่อง)

   ```
   http://localhost
   http://localhost:5173
   ```

   ไม่ต้องใส่ Authorized redirect URIs
5. คัดลอก **Client ID** (ลงท้ายด้วย `.apps.googleusercontent.com`) ใส่ใน `apps/api/.env`

   ```
   GOOGLE_CLIENT_ID=xxxxxxxx.apps.googleusercontent.com
   ```

6. รีสตาร์ต API บรรทัด `เข้าสู่ระบบด้วย Google: เปิด` จะขึ้นตอนเริ่มระบบ และปุ่ม Google จะแสดงที่หน้าเว็บเอง

ตอนขึ้นคลาวด์ (WP7) เพิ่มโดเมนจริงของหน้าเว็บใน Authorized JavaScript origins และเปลี่ยน OAuth consent screen เป็น In production

### 12.3 ทดสอบ

`npm run test:api` จำลองเซิร์ฟเวอร์กุญแจของ Google แล้วทดสอบครบวงจร (สมัคร, OTP, เข้าสู่ระบบ, ผูกบัญชี, token ปลอม, ลบบัญชี)
โดยไม่ต้องมี Client ID จริง ส่วน `test/google.test.js` ทดสอบการตรวจ token แยก
